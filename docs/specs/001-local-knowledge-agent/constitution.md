| 规范编号 | `LKA-001`  |

## 规范用语

本文中的“必须”“禁止”“应当”“不应当”和“可以”表示不同约束强度。违反“必须”或“禁止”的实现，在开始编码前必须先修改本原则并说明原因。

## 1. 产品身份

本项目必须保持为一个自主运行的本地知识整理 Agent，而不是被动的文件上传页面，也不是通用聊天机器人。

系统中必须存在以下五阶段闭环：

1. **观察（Observe）**：检测新增或变化的本地数据源。
2. **决策（Decide）**：识别来源和内容类型，选择处理路径。
3. **执行（Act）**：解析、去噪、分块、去重、提取、分类和索引。
4. **评价（Evaluate）**：检查结构、来源、重复情况和内容质量。
5. **恢复（Recover）**：对临时错误重试，对能力缺失进行降级，对不确定结果转人工审核。

聊天不是 Agent 身份的必要条件。如果后续删除了决策、质量反馈和恢复环节，只保留一次性的固定转换脚本，项目必须改称“本地 RAG 加工管线”，不能继续把 Agent 作为核心卖点。

## 2. 本地优先和隐私默认保护

- 原始内容和学习资料默认必须保存在用户本机。
- 本地 HTTP 服务默认必须只绑定回环地址。
- API Key 必须来自环境变量或本地配置，禁止写入仓库。
- 向模型提供商发送的内容必须限制为当前处理步骤所需的最小范围。
- 用户可以禁止某个来源调用远程模型，同时继续使用本地关键词检索。
- 日志默认禁止记录完整文件正文、完整会话或密钥。

## 3. 来源优先于生成

- 每个知识单元必须关联稳定的来源 ID 和来源版本。
- 模型生成的结论必须能够追溯到本地文件、工具会话或导入记录。
- 主题学习资料中的章节必须引用其所依据的知识单元。
- 系统禁止把没有来源依据的模型生成内容伪装成本地学习资料。
- 来源删除、更新或被替代时，系统必须留下可审计记录。

## 4. 人类可读的主数据

- 带 YAML frontmatter 的 Markdown 必须继续作为知识内容的规范表示。
- SQLite、关键词索引和 HNSW 文件必须被视为可重建的运行状态。
- 数据库或 ANN 索引损坏不得造成已审核知识内容丢失。
- 存储结构必须有版本号，迁移不得破坏既有 Markdown 内容。

## 5. 先审计，后发布

- 所有候选知识在正式发布前必须进入持久化审计队列。
- 质量判断必须使用 `accept`、`review`、`reject` 三种明确状态。
- 模型不可用、输出不合法或无法解析时，禁止默认放行。
- 对不确定内容和冲突内容必须提供人工处理出口。
- Markdown、SQLite 和向量索引必须使用同一个稳定知识 ID。

## 6. 幂等和增量处理

- 重复处理同一份未变化的来源版本，不得产生重复知识单元。
- 文件更新必须沿用稳定来源 ID；语义身份未变化时应沿用知识 ID。
- 同一知识 ID 的并发事件必须串行处理。
- 派生索引应增量更新，并且必须支持确定性全量重建。
- 中断后的事件必须可以安全重试。

## 7. 显式模型边界和可见降级

- 所有知识加工 LLM 和 Embedding 请求必须经过不含聊天事件类型的 `KnowledgeModelAdapter`。
- 提供商差异必须封装在 provider 边界内部。
- LLM 不可用时，系统仍必须支持发现文件、解析、查看既有资料和关键词检索。
- Embedding 不可用时，系统必须降级到关键词和元数据检索。
- 降级状态必须同时对用户界面和结构化日志可见。

## 8. 检索质量必须可测量

- 检索必须具有版本化评测集。
- 每次检索逻辑变化前后必须测量 Recall@k 和 MRR。
- 搜索结果必须暴露足以排查问题的命中渠道或分数说明。
- 禁止仅凭人工挑选的演示查询判断检索质量。
- 本规范实施后，排序不得依赖推断出的用户画像。

## 9. 严格控制产品范围

以下能力不属于目标产品，禁止以隐藏入口或“暂时保留”的方式继续进入生产依赖链：

- 通用聊天和聊天会话持久化。
- 用户画像推断和个性化排序。
- 面向聊天人格的 Prompt 编辑。
- 面向聊天的 MCP 和 Skills 工具执行。

只有仍被知识加工链实际使用的通用基础设施可以保留。没有现行需求、仅以“以后可能使用”为理由存在的模块，应当删除或移出生产依赖链。

## 10. 可测试、可观察、可解释

- 每个处理阶段必须具有明确的类型化输入输出。
- 错误必须说明来源、阶段、事件 ID 以及能否安全重试。
- 单元测试必须覆盖确定性转换和状态迁移。
- 集成测试必须覆盖从监听到发布以及索引重建。
- 浏览器测试必须覆盖来源配置、人工审核、搜索和阅读主流程。
- 宣布改造完成前，类型检查、严格 Lint、测试、检索评测和生产构建必须通过。

## 治理规则

1. `spec.md` 负责需求和验收标准。
2. `design.md` 负责架构和技术决策。
3. `tasks.md` 负责任务顺序和验证工作。
4. 需求变化时，必须在同一次变更中更新所有受影响的规范文件。
5. 引入新的运行时依赖必须在 `design.md` 中解释必要性。
6. 架构例外必须形成 ADR 或写入现有偏差表。
7. 在删除生产代码前，必须先确认非目标和删除清单。
