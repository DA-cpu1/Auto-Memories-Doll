## 1. 用户需求

用户只需要自己实际发送的消息，以及 AI 对这些消息给出的最终回答。AI 的思考过程、进度说明、工具调用及工具返回结果，不作为独立内容进入记忆库。

例如，用户询问报错原因，AI 先检查文件、运行命令，再给出最终解释。采集结果只包含用户的问题和最终解释；工具返回的代码、日志、命令输出和中途说明均排除。如果最终解释主动引用了命令或代码，这些引用仍属于最终回答，必须保留。

本规范约束知识加工的输入，不把产品改造成聊天记录备份工具。后续提取、质量评价、人工审核和 Markdown 发布继续遵循 LKA-001。

## 2. 当前问题与事实基线

- `src/lib/tools/session-parser.ts` 的 `parseCodex()` 对每行事件递归提取 `content/text/message/output/response`，没有消息种类、角色或最终阶段白名单。
- 当前实现可能导入工具输出、中途说明、上下文注入和重复事件；无法保证内容只来自实际的人机对话。
- 本机抽查的 `.codex/sessions` 日志存在 `originator: Codex Desktop`。页面预设名为“Codex CLI”，但这个监听目录可以包含桌面端生成的本地记录。
- 抽查格式包括 `response_item.message` 与 `event_msg.item_completed` 两种消息表示，最终回答阶段为 `final_answer`；还存在 `task_complete.last_agent_message`，不能重复当作新回答。
- 本机用户消息的 `content_item_kinds` 可区分 `user.text`、`agents_md.instructions` 和 `environments.environment_context`。仅检查 `role=user` 不足以证明内容由用户发送。
- 当前 `session-parser.test.ts` 仅有 Trae 专项用例，需要补充 Codex 格式和完整采集链路测试。

以上是本机代码和日志结构的观察，不是对所有 Codex 版本日志格式的保证。开发必须以脱敏、版本化 fixture 明确支持范围。

## 3. 范围

### 3.1 本次包含

- `toolType=codex` 的本地 JSONL 来源，包括受支持格式的 Codex CLI 和 Codex 桌面端记录。
- 首次扫描、文件追加、手动扫描、重启恢复均使用同一内容筛选规则。
- 确定性消息筛选、轮次归属、镜像事件去重、未完成轮次等待及最小诊断信息。
- 来源类型的显示名称更准确地覆盖 CLI 和桌面端，保留既有配置 ID 和目录。
- 从解析结果到模型输入、候选正文、来源摘录及正式知识的过滤边界验证。

### 3.2 本次不包含

- 不修改 Codex 的原始会话文件，不改变 Codex 自身记录工具事件的行为。
- 不读取加密推理，不还原或推断隐藏思考；不新增终端、工具进程或工具输出目录监听。
- 不接入云端、远程主机或其他用户目录，不保证桌面端全部任务都在当前本地目录。
- 不改 Claude Code、Cursor、Trae、Markdown/Text 和 `/api/listen` 的采集规则。
- 不自动清洗已发布的旧笔记、旧候选及索引，不提供历史数据批量迁移工具。
- 不处理图片、音频和附件二进制；消息中用户实际输入的说明、链接或最终回答中的引用可以保留。
- 不增加“采集所有事件”或“包括思考过程”开关，不新增聊天 UI。

## 4. 采集规则

### FR-001：内容必须来自允许的消息

采集范围固定为真实用户输入与明确面向用户的 AI 最终回答。判断依据必须来自已识别的事件 schema、角色、阶段和来源元数据；禁止用 LLM 猜测、按文本长度判断，或把“文件最后一条 assistant”当作最终回答。

| 内容类别 | 是否保留 | 条件 |
| --- | --- | --- |
| 用户问题、补充、纠正、实际粘贴的代码或日志 | 是 | 能确认是真实用户消息，并归属已完成轮次 |
| AI 最终回答 | 是 | 明确的最终阶段，或受支持格式的等价完成证据 |
| 最终回答内的代码块、命令、链接、引用及工具结果摘要 | 是 | 原本就在最终回答正文中，不额外展开原始工具记录 |
| AI 中途说明、执行计划、`commentary`、`analysis` | 否 | 即使其内容看似有用也不采集 |
| 推理事件、推理摘要、明文推理片段及加密推理字段 | 否 | 不读取为业务正文，也不进入诊断正文 |
| 工具调用参数、工具返回值、终端输出、浏览器结果、文件差异事件 | 否 | 独立事件一律排除 |
| system/developer、AGENTS 指令、环境上下文、压缩摘要、后台通知 | 否 | 根据结构化身份排除，不按正文关键词全局删除 |
| 子代理或后台自动任务的内部消息 | 否 | 有可识别的非用户会话/消息来源时排除；不能冒充真实用户输入 |
| 未识别事件、无法证明是最终回答的 assistant 文本 | 否 | 计入诊断，不递归抓取文本兜底 |

同样的工具日志如果由用户主动粘贴到问题中，属于用户输入。不能因为出现 `tool`、`analysis`、`AGENTS.md` 或某个 XML 标签就删除合法正文。

### FR-002：兼容 CLI 和桌面端，保持来源身份

显示名称使用“Codex（CLI / 桌面端）”，内部继续使用 `codex`。不因显示名变化修改已有来源 ID、会话路径、来源版本规则或知识 ID。已有用户自定义的来源名称不得被强制覆盖。

同一目录可能包含不同入口创建的会话；是否支持由事件格式决定，不通过客户端名称绕过筛选。不同文件的相同文本不得在解析器中全局去重。

### FR-003：保留完整轮次，等待最终回答

- 一个采集轮次包含该轮实际用户输入，以及已确认完成的最终回答。多条中途用户补充按原顺序保留。
- 只存在用户消息、中途回答或工具事件时，该轮暂不生成候选，也不调用知识加工 LLM/Embedding。后续追加最终回答后再采集。
- 会话包含多个轮次时，已完成轮次可独立进入后续流程，末尾未完成轮次暂不加入正文。
- 取消、失败或截断且没有明确最终回答时，不用最后一条中途消息代替。明确输出给用户的最终拒绝或失败说明仍是有效最终回答。
- “最终”是每轮对话的最终回答，不是整个会话仅保留最后一句。原始完成消息存在多个合法文本块时按原顺序拼接。
- 无法可靠归属用户输入的最终回答不得错误配对上一轮或下一轮，记录 `orphan_final`。
- 本次采用“用户单独输入等待最终回答”的产品规则；不把未获回复的问题单独发布为笔记。

### FR-004：同一逻辑消息只保留一次

同一消息可能同时出现在 `response_item`、`item_completed`、`agent_message` 或完成事件快照中。按会话、轮次和消息身份合并镜像事件，优先使用结构更完整的表示。去重范围限于同一逻辑消息；用户在不同轮次重复输入相同文本必须保留。

没有稳定消息 ID 时，只允许在已确认的同轮镜像关系内，结合角色、最终阶段和正文指纹去重。禁止跨轮按正文集合去重，禁止将完成事件的快照再追加成一条回答。

### FR-005：过滤必须先于知识加工

原始日志只能供本地结构解析和原始 revision 计算使用。只有允许的对话内容可以进入标题、摘要、语义分块、来源摘录、候选记录、LLM/Embedding 请求和新发布的 Markdown。

过滤必须先于 `limitSessionContent()`、文本归一化和分块，避免噪声占满长度预算。消息解析不得对正文进行模型改写；原有长度限制若截断允许内容，必须可观察，不得把截断结果标记为完整会话备份。

来源追溯可以保存原文件路径、行号、消息/轮次 ID、原始 revision 和哈希。诊断和失败归档不得为了说明过滤原因复制被排除的正文。用户主动打开本地原文件仍会看到 Codex 自己保存的完整日志。

### FR-006：追加噪声不产生业务更新

保持现有 `SourceRevisionEvent` 的原始字节 revision 和稳定 event ID，不用过滤后的正文替换原始 revision。文件只追加工具、推理、进度或统计事件时，观察记录可以变化，但允许内容未变化必须成为无操作：不新增候选、不调用知识加工模型、不修改已发布笔记。

真正新增已完成对话时，沿用现有来源与知识更新链路。重复扫描、进程重启和只追加镜像消息不得反复入队。仍须保证同一 `memoryId` 串行消费及审核后发布。

### FR-007：解析异常不放宽规则

- 使用显式 schema 校验支持的事件。未知事件默认跳过，禁止回退到递归提取任意 `text/output`。
- JSONL 尾部半行允许等待下次完整写入；损坏行记录计数，不能使其两侧无法关联的消息被错误拼接。
- 缺少阶段或轮次证据的旧格式，只有加入确定性适配规则及正反例 fixture 后才能支持；否则标记为不支持的格式。
- 过滤计数及原因必须区分“等待最终回答”“只有非对话事件”“格式无法识别”与 I/O 失败。前三者不能造成无限重试或错误触发模型降级。

### FR-008：历史边界与兼容

首次扫描尚未处理过的历史文件，也必须按新规则过滤。已处理且原始 revision 未变的旧记录保持现有幂等语义，本版本不因 parser 升级自动全量重跑。

已存在的笔记、候选和归档不追溯保证满足新规则，旧候选仍可能被原队列处理；发布说明必须明确该限制。需要清洗历史数据时另行制定可预览、可审计的迁移需求，禁止以过滤为空为理由直接删除旧知识。

## 5. 验收场景

| 编号 | 输入或操作 | 必须得到的结果 |
| --- | --- | --- |
| AC-01 | 一轮用户问题、commentary、reasoning、工具输出、最终回答 | 解析正文只包含问题与最终回答 |
| AC-02 | 桌面端 `final_answer` 及已支持 CLI 最终阶段格式 | 均识别；结构白名单明确且有 fixture |
| AC-03 | 同一消息的 response/item/completion 镜像 | 用户消息与最终回答各保留一次 |
| AC-04 | 用户跨两个轮次发送相同问题 | 两次真实输入均保留，不跨轮误去重 |
| AC-05 | 最终回答包含代码、命令、日志引用或词语 analysis | 正文不因关键词被误删 |
| AC-06 | role=user 的 AGENTS/环境上下文与真实输入并存 | 排除注入块，保留实际用户输入 |
| AC-07 | 用户在 AI 执行期间追加纠正或补充 | 已完成轮次保留这些输入的原始顺序 |
| AC-08 | 已完成第一轮，第二轮只有问题和工具输出 | 仅采集第一轮；第二轮最终回答到来后才更新 |
| AC-09 | 只有中途消息、取消事件，或未知 assistant 格式 | 零候选、零知识加工模型调用，有明确原因 |
| AC-10 | 只追加工具事件、token 统计或镜像回答，再重启扫描 | 不增加待审计事件，不修改笔记，不调用模型 |
| AC-11 | 尾部 JSON 半行后补全最终事件 | 第一次不误采，补全后恰好采集一次 |
| AC-12 | 损坏行打断无法确认的轮次关系、孤立 final | 不跨轮拼接；已能独立确认的完整轮次仍可处理 |
| AC-13 | 被排除事件放置独特哨兵字符串 | 新候选、来源摘录、远程请求、诊断正文和新笔记均无该字符串 |
| AC-14 | 相同内容处于两个不同来源文件 | parser 不跨来源去重，来源引用各自正确 |
| AC-15 | 未识别格式、子代理内部会话、无可采文本的附件消息 | 不将其伪装为真实用户与最终回答；原因可见 |
| AC-16 | 过滤后内容超过既有预算 | 只对允许内容截断，截断可见，不恢复被排除事件 |
| AC-17 | 未配置模型或模型调用失败 | 确定性过滤仍有效，候选继续遵循既有 review 降级策略 |
| AC-18 | 已处理旧版本、未处理历史文件、其他工具来源回归 | 按 FR-008 执行；不自动清洗旧数据，其他解析器行为保持兼容 |
