## 1. 用户需求

用户需要自动采集和整理知识，不应因为可选的向量模型不可用，就被要求逐条审核数百条候选。用户问题与 AI 最终回答的确定性筛选不依赖 Embedding；可用的 LLM 应继续完成质量检查和知识提取。

本规范要求：Embedding 不可用时使用确定性去重与关键词召回；只有必要的 LLM 不可用时等待服务恢复。人工审核用于内容冲突、质量存疑或证据不足，不承担基础服务故障的批量确认工作。

本规范不承诺所有候选都自动发布。自动发布仍须通过有效的质量判断、证据校验、结构校验和既有审计流程。

## 2. 当前问题与事实基线

以下结论来自 `a754b8d` 的代码和本次会话中已完成的只读检查：

- 用户截图中的“待审核 325”是全应用 325 条候选的总数，不是一条记录需要 325 次审核。当时数据库中这些候选对应 325 个来源，原因均为 `VECTOR_RECALL_UNAVAILABLE`；这是当时的状态，不是固定测试数量或当前实时统计。
- `Orchestrator.recallSimilarMemories()` 在全局降级或向量请求失败时返回 null；`ingestByExtraction()` 随即把候选置为 review，尚未执行质量检查就结束。
- `KnowledgeModelAdapter.isDegradedMode` 合并了 LLM 和 Embedding 的故障状态。质量检查、提取与话题分类使用这个总开关，Embedding 单独故障也会抑制 LLM 工作。
- 健康检查先调用 Embedding，再调用 budget LLM。前者失败会阻止后者探测；budget 成功也不能证明实际用于质量检查的旗舰模型可用。
- 队列只有 pending/processing/done/failed/rejected/review，没有明确、持久化的服务依赖等待状态。review 不会因为服务恢复自动重新处理。
- 现有文本相似度辅助函数包含移除非 ASCII 字符的逻辑，不应直接作为中文知识的确定性查重依据。

关键位置：`src/lib/ai/knowledge-model-adapter.ts`、`src/server/services/orchestrator.ts`、`quality-filter-service.ts`、`memory-extraction-service.ts`、`topic-classification-service.ts`、`src/server/pipelines/deduplicator.ts`。

## 3. 范围

### 3.1 本次包含

- 进入统一知识循环的文件、工具会话和 listen 候选，以及既有更新处理中的同类模型依赖。
- 按能力判断可用性，解除 Embedding 对 LLM 质量检查、提取和话题分类的误阻断。
- 无向量时的精确内容去重、关键词相似候选召回，以及明确可观察的降级信息。
- 服务依赖等待、有限自动重试、恢复后的继续处理，以及发布后的向量补建。
- 首页计数、审核列表和来源/进度 API 对人工审核与服务等待的区分。
- 对符合条件的旧故障审核候选提供可预览、可审计、可重复执行的批量重新处理。

### 3.2 本次不包含

- 不改变 KA-002 的真实用户/最终回答筛选、轮次等待、截断和原始 revision 规则。
- 不提供绕过全部质量检查的“全部接受”，不把关键词相似度当作语义等价证明。
- 不降低现有质量阈值，不把推断、假设或证据不足内容自动提升为已确证事实。
- 不删除外部会话原文件，不重新导入用户已删除的来源，不擅自启用监听。
- 不自动重跑已完成或已拒绝事件，不全量改写已发布笔记，不把已发布知识撤回重新审核。
- 不新增聊天、MCP、Skills 运行时，不更换向量数据库或引入新的 AI 提供商。

## 4. 目标行为

以下矩阵以候选正文非空、基础校验通过为前提；“LLM 可用”指当前阶段实际需要的模型可用。

| Embedding | 必要 LLM | 候选行为 | 发布与检索 |
| --- | --- | --- | --- |
| 可用 | 可用 | 既有向量召回、质量检查和提取流程 | 通过审计后发布，支持向量与关键词 |
| 未配置、主动关闭或调用失败 | 可用 | 精确去重与关键词召回后继续质量检查、提取 | 满足发布条件即可发布；关键词可检索，向量状态单独记录 |
| 可用 | 不可用 | 保留候选，进入“等待模型服务” | 不发布未经有效质量判断的内容；已发布知识仍可检索 |
| 不可用 | 不可用 | 确定性筛选和去重可运行，候选等待必要 LLM | 不因此进入人工审核，不发布；已有关键词检索继续可用 |

独立于能力矩阵：确定重复可以结束为跳过/拒绝，真实内容疑点进入人工审核，存储或事务故障走独立的可恢复错误路径。

## 5. 功能要求

### FR-001：能力与健康状态分离

1. LLM 任务只受该任务所需模型的可用性影响；Embedding 故障不得阻止可用的 LLM。
2. Embedding 调用不因 LLM 故障而被禁止。两类健康探测独立执行、独立更新状态，互不作为前置条件。
3. 配置存在不等于服务可用，健康探测成功也不代替实际请求错误处理。budget 模型成功不能清除旗舰模型的已知故障。
4. 前端和进度数据至少区分 llm/embedding，并能指出当前等待的实际任务或模型槽位；技术设计须确定最小类型和持久化方案。
5. 所有模型调用仍经过 `KnowledgeModelAdapter`，不引入新的跨层全局状态或 UI 回调契约。

### FR-002：Embedding 是可选能力

- 用户可明确关闭 Embedding；默认保留升级前的启用意图、模型、维度及配置。关闭后不再执行向量生成、健康探测或补建请求。
- 未配置与主动关闭不能被反复当作网络故障重试。若 Embedding 使用共享 API Key，不得把“清空专用 Key”误解释为主动关闭。
- 启用但服务故障时，当前候选可降级处理；同一故障期间使用能力级退避，不能对每条候选重复探测已知不可用的端点。
- 可用向量的既有召回与去重行为保持兼容。ANN 本地故障应先使用既有可用后端降级能力，不能把它误报成 LLM 故障。

### FR-003：确定性去重与关键词召回

1. 来源 event ID、revision 与允许正文 hash 的既有幂等判断仍在模型调用之前执行。相同来源内容、噪声追加、重启和重复扫描不能新增候选或再次调用模型。
2. 无向量时，对已发布内容和未完成候选进行精确内容身份检查。中文、代码符号、数字和否定词必须保留；不得以删除这些字符后的相同结果判重。
3. 同一 memoryId 的内容变更必须进入更新流程；比较时排除自身当前记录，不能把自身命中当作重复而丢失更新。
4. 不同来源正文完全相同时，去重结果仍须保留来源引用；不得覆盖已有来源、生成无法追溯的合并结果，或删除外部原文。
5. 关键词召回只提供有限数量的潜在相似记录作为 LLM 质量判断参考，不因高词语重合直接自动拒绝或合并。不得伪造 cosine similarity 或向量得分。
6. 无关键词命中不代表已证明语义新颖。向质量检查提供“仅关键词召回”的明确上下文，接受其后续 accept/review/reject 判断。
7. 关键词索引是可重建缓存。索引故障应明确记录并使用可用的本地回退；本地数据库读取失败不能伪装为“没有重复”。

### FR-004：自动发布继续执行质量与审计

- 仅 Embedding 不可用时，必须尝试执行可用的质量检查、知识提取和必要分类，不能在向量召回失败处直接转 review。
- 自动发布须保留现有 accept/review/reject 阈值、知识类型约束、来源证据、结构校验、版本冲突处理及 Markdown 写回规则。
- 质量判断为明确低质时按现有规则拒绝；质量存疑、非事实、缺少证据、候选与现有内容冲突时才转人工审核，并给出内容原因。
- LLM 超时、限流、鉴权失败、缺少配置或结构化输出不可用属于加工依赖故障，不能伪装成“评分存疑”。未经有效加工的半成品不得自动发布。
- 同一 memoryId 的消费和恢复必须串行。更新失败或等待服务期间保留已发布版本，不先删除旧版本再等待新结果。

### FR-005：服务等待是独立、持久化状态

为未能完成必要模型加工的候选建立独立的“等待模型服务”语义（建议状态名 `waiting_dependency`，最终代码名由技术设计确定）。

必须记录：原事件与 memoryId、阻塞阶段和能力、结构化原因、已尝试次数、下次允许尝试时间、是否已暂停自动重试。复用来源和处理进度契约，不只在日志或浏览器内存中保存。

- 这些候选不计入人工审核数量，不混入默认人工审核列表；它们尚未发布，必须仍能在等待列表中查看和处理。
- 队列普通消费不能无视等待时间重新执行；服务等待与存储故障重试使用不同原因和调度条件。
- 进程重启保留等待状态、尝试次数和期限，不能重置预算后立即重试整批。
- 同一事件只能处于一种当前队列状态；历史进度可以保留多个阶段，不能用于重复累计当前候选数。
- 等待期间出现同一来源新版本时，保留既有串行和版本校验；旧版本不能在恢复后覆盖新版本。明确标记被替代事件，不静默丢失人工编辑。

### FR-006：恢复与成本控制

- 短时失败默认采用最多 3 次自动重试，分别在约 1、5、20 分钟后尝试，可加入抖动；实现须集中配置这些参数。
- 缺少配置、主动关闭、无效凭证等需要配置变化的状态，不逐候选持续请求。提示配置问题，配置变更或用户明确重试后重新检查。
- 用尽自动重试次数后，候选继续停留在服务等待列表并标记“自动重试已暂停”，不因此批量转入人工审核或丢弃。
- 恢复探测成功可唤醒未暂停的相关候选；用户重试或相关配置变更可恢复已暂停候选。唤醒时沿用原事件身份，记录新 attempt，不克隆候选。
- 恢复处理按有界批次运行，建议默认每批最多 20 条，并遵守既有模型并发池；同一恢复任务不可重叠执行。数百条积压不能瞬间并发请求远程模型。
- 实际模型请求仍可能失败；再次失败应回到相应等待状态。LLM 恢复不能被 Embedding 故障阻挡。
- 批量重新处理与自动恢复都不得反复执行已经完成的有效加工阶段；能否复用中间结果必须以同一候选内容和模型/策略版本为依据。

### FR-007：发布后向量补建

- 无向量发布的笔记必须可通过关键词检索，并记录其向量状态为待生成、生成失败或主动关闭；不得显示成已完成向量索引。
- Embedding 恢复后，只补建当前仍存在、需要向量的已发布知识；不重跑内容提取、审核或 Markdown 发布，不增加知识副本。
- 补建记录必须校验 memoryId、当前内容版本/hash、模型和维度。已删除笔记、旧内容版本和旧模型任务不得在异步完成后回写为有效向量。
- 切换 embedding 模型或维度时，继续执行现有索引重建与版本一致性约束，旧向量不能混用于新模型查询。
- 补建同样受并发、退避及批次限制；用户关闭 Embedding 后应停止新请求。
- 降级期间可能遗漏语义近似重复，这是可观察的能力差异。恢复补建不能悄悄合并或删除已发布知识；后续语义清理属于单独维护流程。

### FR-008：旧故障审核积压的重新处理

提供“重新处理服务故障候选”操作，先返回按原因、来源和状态分类的预览，再由用户确认执行；本规范的编写不代表授权现在迁移运行数据。

1. 首次范围只自动识别当前仍为 review、原因明确为 `VECTOR_RECALL_UNAVAILABLE` 且没有人工编辑或决策痕迹的候选。人工审核原因、混合原因或无法证明原因的候选留在原处，并在预览中说明。
2. 旧 LLM 故障可能与内容质量疑点共用原因码；没有明确历史证据时不得按错误文案批量迁移。后续支持必须增加确定性识别与正反例测试。
3. 对 Codex 候选，必须确认候选关联的来源版本经过 KA-002 筛选。缺少策略版本证据时，不直接将旧候选正文送往模型；在预览中单独标记需兼容处理，不自动全量重读原始会话。
4. 迁移重用原 pending event ID、source event ID、revision 和 memoryId，记录迁移批次、前后状态、原因与处理结果；不伪造新来源 revision。
5. 执行时重新核对状态与候选版本。预览后已被接受、拒绝、编辑、删除或正在处理的记录必须跳过，不能覆盖用户动作。
6. 合格候选进入新流程重新查重和质量检查；必要 LLM 不可用则转服务等待，不直接自动接受。已经人工接受的 done 记录完全不参与，即使还保留旧故障原因码。
7. 来源被停用不会自动删除或恢复其已有候选；用户可在预览中明确选择这些候选，但迁移不得启用监听、读取已删除来源或重建已被清除的数据。
8. 批次可暂停并在重启后继续；重复执行不重复入队或重复发布。记录只含必要标识和计数，不复制原正文或凭据。

### FR-009：计数与用户界面

- 首页分别展示“待处理”“等待模型服务”“待人工审核”“处理失败”；每个数值计的是当前候选数。已登记来源数独立，不称为聊天条数或审核次数。
- 只有 Embedding 不可用时，提示实际影响，例如“语义检索不可用，关键词检索和知识加工继续运行”；必要 LLM 不可用时提示“知识加工等待模型服务恢复”。不再统一提示所有模型故障都要人工审核。
- 服务等待列表显示原因、阻塞任务、上次尝试、下次重试或暂停状态，提供重试入口和相关设置入口；缺少凭据时不提供会无条件触发整批请求的操作。
- 人工审核列表保留来源对照和具体内容原因；批量迁移入口显示符合条件数、跳过数和处理进度。
- 向量补建状态与候选审核状态分别展示；关键词可检索但无向量的已发布笔记不能被标为未发布。
- UI、API 响应 schema、队列类型、事件状态机、持久化迁移和统计查询必须同步，不能只改标签掩盖 review 队列。

### FR-010：隐私、兼容与架构约束

- 确定性过滤、敏感信息脱敏和内容预算仍在远程请求之前执行，健康检查只使用固定探测文本。
- 日志及故障诊断不得输出 API Key、候选完整正文、被 KA-002 排除的内容或原始模型输出片段。
- 保持审计后发布、稳定来源身份、Markdown 主数据、SQLite 队列与可重建索引的架构边界。
- 本规范在实施后替代既有文档中“单独 Embedding 故障必转人工”和“纯服务故障一律人工审核”的策略；fail-closed 的含义仍是无有效质量判断不得自动发布。内容疑点的人工裁决规则不变。
- 升级时不把旧 review 全部改成等待状态；旧数据兼容严格按 FR-008 执行。实现须更新 `Agents.md` 的偏差表与路线图。

## 6. 验收场景

| 编号 | 场景 | 必须得到的结果 |
| --- | --- | --- |
| AC-01 | Embedding 未配置，必要 LLM 可用 | 非重复且质量接受的候选自动发布，无故障型人工审核，关键词可检索 |
| AC-02 | Embedding 超时/空向量/限流，LLM 可用 | 采用降级召回继续加工；记录真实能力和原因，不伪造向量分数 |
| AC-03 | 有共享 Key，用户主动关闭 Embedding | 不调用 Embedding、健康探测或补建；LLM 仍工作，配置重启后保留 |
| AC-04 | 只有 LLM 故障或两者均故障 | 候选进入服务等待；不自动发布，不计入人工审核；现有检索按可用能力继续 |
| AC-05 | budget 可用但旗舰失败；Embedding 探测失败 | 不错误清除旗舰故障；两类探测独立，失败互不阻塞 |
| AC-06 | 中文、数字、否定词或代码符号不同 | 不被破坏性规范化误判为精确重复；关键词近似只作为质量参考 |
| AC-07 | 同来源无变化、噪声追加、重复扫描和重启 | 不新增候选、不重复知识加工请求，来源原始 revision 规则保持 |
| AC-08 | 两来源正文相同或同时进入相同候选 | 幂等且保留来源引用，不生成无来源副本，不因并发重复发布 |
| AC-09 | 更新命中自身，或等待旧版本晚于新版本恢复 | 不误拒绝合法更新，旧版本不覆盖新版本；等待期间现有笔记保留 |
| AC-10 | 质量存疑、非事实、证据不足或字段冲突 | 保持人工审核和明确内容原因；Embedding 恢复不能自动放行 |
| AC-11 | 模型返回非法 JSON 或输出不可用 | 有限尝试后进入服务等待/暂停，不当作有效 accept，不无限逐条重试 |
| AC-12 | 未到期限、重启、重试耗尽或缺少凭据 | 等待状态和预算持久化；不立即整批请求、不转人工审核或丢弃 |
